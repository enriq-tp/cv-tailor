## Database (Task 2)

### Concepts

- **Container**: an isolated process running Postgres with its own filesystem. It does not touch the PostgreSQL 18 service installed natively on this Windows machine.
- **Volume**: Docker-managed disk (`cv_tailor_pgdata`) holding the data. It survives removing the container; it is deleted only on purpose.
- **Connection string** (`DATABASE_URL`): `postgresql://USER:PASSWORD@HOST:PORT/DB`. It tells a client how to reach the database.
- **Prisma Client**: TypeScript code generated from `prisma/schema.prisma`. The app uses it instead of hand-written SQL.

### How the pieces connect

```
.env ──► docker-compose.yml ──► container "cv-tailor-db" (postgres:18, port 5432 inside)
 │                                      ▲
 │                                      │ 127.0.0.1:5433 on this PC
 └─ DATABASE_URL ──► prisma7.config.ts (CLI)  and  scripts/db-check.ts (runtime)
                                         └─► PrismaClient + @prisma/adapter-pg (pg driver)
```

- **Host port 5433**, not 5432: the native Windows PostgreSQL already uses 5432. The mapping is `127.0.0.1:5433:5432`, so the database is only reachable from this PC.
- **How Prisma finds `DATABASE_URL`**: Prisma 7 does not read `.env` by itself. `prisma7.config.ts` starts with `import "dotenv/config"`, which loads `.env` into `process.env`, and then sets `datasource.url` from `process.env["DATABASE_URL"]`. The runtime code (`scripts/db-check.ts`, later `src/lib/`) does the same import and passes the string to the `PrismaPg` adapter. The schema file has no `url` in Prisma 7.
- **Why `prisma7.config.ts`**: Prisma 7.10 names its config this way so it does not clash with the Prisma 8 name. The CLI loads it automatically ("Loaded Prisma config from prisma7.config.ts").
- **Credentials** are read from `.env` by Compose and are used only on the first start, when the volume is empty. Changing `POSTGRES_PASSWORD` later does not change the existing database; reset the volume (below).

### Commands (Git Bash, from the project root)

```bash
docker compose up -d                 # start (creates container + volume the first time)
docker compose ps                    # status; wait for "(healthy)"
docker compose logs -f db            # follow logs (Ctrl+C to leave)
docker compose stop                  # stop, keep data
docker compose down                  # remove container, KEEP data (volume stays)
docker compose down -v               # Reset: remove container AND delete all data
npm run db:generate                  # regenerate generated/prisma (needed after a fresh clone, a schema change or a migration: Prisma 7 migrate dev does not do it)
npm run db:migrate -- --name <name>  # create + apply a migration after editing prisma/schema.prisma
npm run db:studio                    # Prisma Studio in the browser; it prints its URL
npm run db:check                     # connect through Prisma and run SELECT 1
npm test                             # logger privacy tests (node:test, run by tsx)
docker exec -it cv-tailor-db psql -U cvtailor -d cvtailor   # open psql inside the container
```

Reset when `.env` credentials changed: `docker compose down -v`, then `docker compose up -d`, then `npx prisma migrate deploy` (re-creates the tables from the committed migrations) and `npm run db:generate`.

Reset only the data, keeping the same container and credentials: `npx prisma migrate reset` (drops everything and re-applies all migrations; it asks for confirmation).

### Setting up on a fresh clone

1. Copy `.env.example` to `.env` and replace `change_me` (use the same password in `POSTGRES_PASSWORD` and inside `DATABASE_URL`).
2. `npm install`, `docker compose up -d`, `npx prisma migrate deploy` (creates the tables), `npm run db:generate`, `npm run db:check`.

## Agents (Claude Code subagents)

Four subagents live in `.claude/agents/` (tracked in git, shared with the repo). Each is a Markdown file: a YAML frontmatter (`name`, `description` = when Claude should use it, `tools` = what it may call, `color`) and a body that is its system prompt (owned folders, forbidden folders, the CLAUDE.md rules that matter in its area, and what to update when it finishes). The workflow rules (one branch per task, PRs to `main`, reviewer before merge) are in `CLAUDE.md`.

| Agent      | Owns                                                                                              | Tools                                                    |
| ---------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `infra-db` | `docker-compose.yml`, `prisma/`, `prisma7.config.ts`, `scripts/`, `src/lib/db.ts`, `src/app/api/health/` | Read, Grep, Glob, Edit, Write, Bash, PowerShell, WebFetch |
| `frontend` | `src/app/` (not `api/`), `src/components/`, `public/`, later the PDF template                      | Read, Grep, Glob, Edit, Write, Bash, PowerShell          |
| `backend`  | `src/app/api/` (not `health/`), `src/lib/` (not `db.ts`, `logger.ts`), `src/agents/`               | Read, Grep, Glob, Edit, Write, Bash, PowerShell, WebFetch |
| `reviewer` | Nothing (read-only review of the branch diff against `main`)                                      | Read, Grep, Glob, Bash (Edit, Write, NotebookEdit, PowerShell removed) |

Shared files (`src/lib/logger.ts`, `src/lib/logger.test.ts`, `package.json`, `package-lock.json`, `.env.example`, `next.config.ts`, `tsconfig.json`, `eslint.config.mjs`, `.prettierrc`) change only when a task requires it. `CLAUDE.md` and `.claude/` are changed by the owner.

**What is enforced and what is not:**

- Enforced by configuration: which tools each agent has (`tools` / `disallowedTools`), and that none can start other subagents (`Agent` is not in any list).
- Not enforced, only instructions in the prompt: the folder limits of every agent, the phase limits, the privacy rules, "never run destructive commands", and "the reviewer must not change anything through Bash".
- The Claude Code docs describe path-level limits only through permission rules in settings (`Edit(path)`, which apply to the whole session) or `PreToolUse` hooks. Neither is used yet. See `decisions.md`.

Each agent files its own wiki update and a `changelog.md` line at the end of its task. Tasks run one at a time, so two agents never edit the same wiki page at once.

## Data flow (target)

PDF -> text loader -> cleaning -> LLM extracts structured JSON (zod) -> match against job JSON -> LLM rewrites only the JSON -> fixed PDF template (`@react-pdf/renderer`) -> PDF. See `CLAUDE.md` for the rules around it.

## Tooling notes

- `.prettierrc` sets `"endOfLine": "auto"`: with Git's `core.autocrlf=true` on Windows, checked-out files use CRLF, and Prettier's default (LF only) would make `format:check` fail on every file.
- ESLint (`npm run lint`) finds code problems; Prettier (`npm run format`) only formats. `eslint-config-prettier` turns off ESLint rules that would fight Prettier. `generated/` is ignored by both.
- `next.config.ts` was generated with `cacheComponents` and `partialPrefetching` enabled (defaults of the current template). Revisit when real pages are built.
- `pino` (dependency) and `pino-pretty` (dev only, readable logs in development) need no `next.config.ts` change: Next.js already lists `pino`, `pino-pretty` and `thread-stream` as external packages (`serverExternalPackages` docs), so they are not bundled. Verified with `next dev` and `next build` + `next start`.
- `src/lib/db.ts` and `src/lib/logger.ts` are server-only. Never import them from a client component (no `"use client"` file).
- Test files (`*.test.ts`) live next to the code and are type-checked by `next build` like any other file; they use only `node:test` from Node, so they add no dependency.
- Prisma is pinned to exactly 7.10.1 (`prisma`, `@prisma/client`, `@prisma/adapter-pg`) so the CLI and client never drift apart.
- `npm` prints "allow-scripts" warnings for Prisma packages' install scripts. They are not needed for `prisma generate` here; ignore unless generation starts failing.
