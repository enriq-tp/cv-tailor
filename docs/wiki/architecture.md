## Database (Task 2)

### Concepts

- **Container**: an isolated process running Postgres with its own filesystem. It does not touch the PostgreSQL 18 service installed natively on this Windows machine.
- **Volume**: Docker-managed disk (`cv_tailor_pgdata`) holding the data. It survives removing the container; it is deleted only on purpose.
- **Connection string** (`DATABASE_URL`): `postgresql://USER:PASSWORD@HOST:PORT/DB`. It tells a client how to reach the database.
- **Prisma Client**: TypeScript code generated from `prisma/schema.prisma`. The app uses it instead of hand-written SQL.

### How the pieces connect

```
.env ──► docker-compose.yml ──► container "cv-tailor-db" (postgres:18, port 5432 inside)
 │                                      ▲
 │                                      │ 127.0.0.1:5433 on this PC
 └─ DATABASE_URL ──► prisma7.config.ts (CLI)  and  scripts/db-check.ts (runtime)
                                         └─► PrismaClient + @prisma/adapter-pg (pg driver)
```

- **Host port 5433**, not 5432: the native Windows PostgreSQL already uses 5432. The mapping is `127.0.0.1:5433:5432`, so the database is only reachable from this PC.
- **How Prisma finds `DATABASE_URL`**: Prisma 7 does not read `.env` by itself. `prisma7.config.ts` starts with `import "dotenv/config"`, which loads `.env` into `process.env`, and then sets `datasource.url` from `process.env["DATABASE_URL"]`. The runtime code (`scripts/db-check.ts`, later `src/lib/`) does the same import and passes the string to the `PrismaPg` adapter. The schema file has no `url` in Prisma 7.
- **Why `prisma7.config.ts`**: Prisma 7.10 names its config this way so it does not clash with the Prisma 8 name. The CLI loads it automatically ("Loaded Prisma config from prisma7.config.ts").
- **Credentials** are read from `.env` by Compose and are used only on the first start, when the volume is empty. Changing `POSTGRES_PASSWORD` later does not change the existing database; reset the volume (below).

### Commands (Git Bash, from the project root)

```bash
docker compose up -d                 # start (creates container + volume the first time)
docker compose ps                    # status; wait for "(healthy)"
docker compose logs -f db            # follow logs (Ctrl+C to leave)
docker compose stop                  # stop, keep data
docker compose down                  # remove container, KEEP data (volume stays)
docker compose down -v               # Reset: remove container AND delete all data
npm run db:generate                  # regenerate generated/prisma (needed after a fresh clone or schema change)
npm run db:check                     # connect through Prisma and run SELECT 1
docker exec -it cv-tailor-db psql -U cvtailor -d cvtailor   # open psql inside the container
```

Reset when `.env` credentials changed: `docker compose down -v` then `docker compose up -d`.

### Setting up on a fresh clone

1. Copy `.env.example` to `.env` and replace `change_me` (use the same password in `POSTGRES_PASSWORD` and inside `DATABASE_URL`).
2. `npm install`, `npm run db:generate`, `docker compose up -d`, `npm run db:check`.

## Data flow (target)

PDF -> text loader -> cleaning -> LLM extracts structured JSON (zod) -> match against job JSON -> LLM rewrites only the JSON -> fixed PDF template (`@react-pdf/renderer`) -> PDF. See `CLAUDE.md` for the rules around it.

## Tooling notes

- ESLint (`npm run lint`) finds code problems; Prettier (`npm run format`) only formats. `eslint-config-prettier` turns off ESLint rules that would fight Prettier. `generated/` is ignored by both.
- `next.config.ts` was generated with `cacheComponents` and `partialPrefetching` enabled (defaults of the current template). Revisit when real pages are built.
- Prisma is pinned to exactly 7.10.1 (`prisma`, `@prisma/client`, `@prisma/adapter-pg`) so the CLI and client never drift apart.
- `npm` prints "allow-scripts" warnings for Prisma packages' install scripts. They are not needed for `prisma generate` here; ignore unless generation starts failing.
